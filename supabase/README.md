# База данных: итерация 1

Четыре файла в `supabase/migrations/` применяются строго по порядку.
Проверены на чистом Postgres 16 (90 проверок: ограничения, права, срез, курсы, закрытие периодов).

## Что внутри
- Справочники: страны, валюты, учреждения, проекты.
- Счета, доступ (`account_access`), признаки счетов (шифрование, поиск по HMAC).
- Операции (сумма со знаком, мягкое удаление), корректировки, контрольные точки.
- Закрытие и открытие периодов, журнал изменений.
- Курсы валют, `get_snapshot`, `get_snapshot_totals`, `get_checkpoint_diffs`, `convert_amount`.

Пока нет: контрагентов, тегов, импортов, переводов и обмена, фирм с процентом.
Колонки `counterparty_id`, `tag_id`, `import_id`, `transfer_id` в операциях уже есть, внешние ключи добавятся вместе с их таблицами.

## Порядок установки (сначала тестовый проект Supabase)

### 1. Ключи шифрования (один раз на проект)
Сгенерируйте два ключа на компьютере и сохраните их в двух независимых местах
(менеджер паролей и ещё одно): `openssl rand -hex 32`.
Ключи нужны для восстановления: Vault не переезжает вместе с дампом базы,
в новом проекте секреты придётся создать заново из ваших копий.

SQL Editor, подставьте свои значения:

    select vault.create_secret('<КЛЮЧ_1>', 'identifier_enc_key',  'Шифрование номеров счетов');
    select vault.create_secret('<КЛЮЧ_2>', 'identifier_hmac_key', 'HMAC для поиска по номерам');

Не используйте один и тот же ключ дважды.

### 2. Миграции
SQL Editor: открыть каждый файл по порядку, вставить, Run.
1. `20261102100000_core_dictionaries_access.sql`
2. `20261102100100_money_tables.sql`
3. `20261102100200_snapshot_and_fx_functions.sql`
4. `20261102100300_period_close_functions.sql`

Повторно файл применять нельзя (таблицы уже будут созданы).

### 3. Ваш пользователь
Authentication → Users → Add user (email и пароль). Включите 2FA позже, в приложении.
Доступ к счетам даёт запись в `account_access`. После загрузки счетов (seed, шаг 3 плана):

    insert into public.account_access (account_id, user_id, role)
    select id, '<UUID_ПОЛЬЗОВАТЕЛЯ>', 'owner' from public.accounts
    on conflict do nothing;

## Что важно знать клиенту
- Справочники и счета создаёт загрузка seed-JSON (сервер, `service_role`) или SQL Editor. Из приложения пока только читаются.
- `account_identifiers`: запрашивать только колонки `id, account_id, kind, last4, valid_from, valid_to`. `select *` вернёт «permission denied» (так и задумано, номера закрыты).
- Жёсткого удаления операций у клиента нет: удаление = `update ... set deleted_at = now()`. Насовсем помеченные записи удаляет `close_period(..., true)`.
- Ошибка закрытого периода начинается с `PERIOD_LOCKED:`.
- Закрытие: `rpc('close_period', {p_project_id, p_through, p_purge_deleted})`; открытие: `rpc('reopen_period', {p_project_id, p_steps, p_reason})`. Только владелец всех счетов проекта.
- Срез: `rpc('get_snapshot', {p_date, p_account_ids, p_base_currency})` строки по счетам, `get_snapshot_totals` итоги по валютам и общий итог. `has_rate = false` значит «нет курса», итог неполный.
- Курс: `1 base = rate quote`. Если пары нет, считается обратная, затем через опорную валюту (`app_settings.fx_pivot_currency`, по умолчанию `uah`). Приоритет источников: `fx_source_priority` (меньше = важнее).
- Округление: только при пересчёте, обычное (половина от нуля), число знаков из `currencies.decimals`. Каждый счёт округляется отдельно, итог = сумма округлённых.
- Остаток на дату считается до конца этого дня в поясе счёта (пояс счёта, иначе пояс страны).
- Архивный счёт с нулевым остатком не показывается в срезах после даты архивации; с ненулевым остатком показывается всегда.
