# Подразделение «Разбор выписок в XLSX» (ветка `statement-xlsx`)

Создано 20.11.2026. Отдельное подразделение приложения Fin-control. **Пока живёт в отдельной ветке `statement-xlsx`**, в `main` сливается после проверки владельцем (раздел 10). Читать целиком перед работой. Решения владельца этого подразделения записаны здесь и в `docs/DECISIONS.md` (журнал, 20.11.2026).

## 1. Зачем
Движения денег надо видеть глазами, а не искать в базе, где «непонятно, что есть, чего нет». Поэтому выписки банков сначала превращаются в **стандартный XLSX** (одинаковые колонки для всех банков), который владелец открывает на телефоне, смотрит, правит руками и проверяет по сверке. В базу движения попадут позже (скорее всего помесячно), когда схема файла устоится. **Сейчас в базу пишутся только контрагенты** (справочник общий и нужен для опознания).

## 2. Отношение к остальному проекту
- Не заменяет и не трогает уже написанную загрузку через ИИ-чат (`docs/IMPORT-DESIGN.md`, на паузе: `docs/TASK-IMPORT-PAUSED.md`). Таблицы `import_jobs` и экраны «Загрузка выписок» этим подразделением не используются.
- Разбор файлов делает код приложения (TypeScript), **ИИ-чат для разбора не нужен**. Выписки (PDF/XLSX) нигде не хранятся.
- Использует существующее: справочник контрагентов (`counterparties`, `counterparty_identifiers`, ядро `identifiers.ts`), счета (`accounts`, `account_identifiers`), хранилище `Storage`.
- Принцип проекта сохраняется: вся логика в `src/core/`, экраны вызывают только ядро, тесты на хранилище в памяти.

## 3. Решения владельца (20.11.2026)
1. Начальный этап: **результат разбора хранится только в стандартных XLSX-файлах** (не в базе). Черновиков импорта в базе нет. Запись движений в базу позже.
2. **Одна выписка = один файл** результата. Внутри может быть несколько счетов или карт одного банка.
3. Заголовки на русском. Колонки листа «Операции» (раздел 17; с 21.11.2026 без «Времени», с «В выписке» и «В базе»). Колонки «тип» нет. Тегов и плановости пока нет (плановость отметим позже по готовым движениям).
4. **Дата** = первая дата выписки. У Словакии это «Dátum zúčtovania» (дата списания). **Время** одно: время карточной операции из описания (если есть; у SEPA пусто); служебного времени не добавляем.
5. **Переводы между своими счетами не выделяем**: это расход на одном счёте и приход на другом; свои счета известны по признакам.
6. **Сверка**: цепочка остатков и итоги выписки. При расхождении файл всё равно создаётся (строки красным, пометка «НЕ СОШЛОСЬ»); владелец может править файл руками и загрузить обратно (пятый шаблон, раздел 7).
7. **Контрагенты идут первыми** (отдельный файл и отдельная процедура, не смешивать с файлом операций; раздел 6).
8. Новое окно в приложении: отдельный экран, кнопка вместо «Движения» в нижнем меню; «Движения» переносится в «Прочее» отдельной строкой (раздел 9).
9. Работа ведётся в **Fin-control на отдельной ветке `statement-xlsx`** (отдельный репозиторий разбора выписок не нужен).

## 4. Порядок работы с выпиской
1. Владелец открывает экран «Выписки», выбирает файл банка (PDF или XLSX).
2. Приложение разбирает файл **в памяти** (шаблон банка, раздел 7), находит счета/карты по признакам.
3. **Шаг контрагентов.** Приложение выдаёт файл контрагентов (раздел 6). Владелец правит, загружает обратно. Приложение проверяет и записывает контрагентов и их признаки в базу.
4. **Шаг операций.** Приложение выдаёт XLSX «Операции + Сверка» (раздел 5) с уже проставленными контрагентами. Файл лежит у владельца (Загрузки/Диск), нигде больше не хранится.
5. Позже: загрузка проверенных файлов в базу (отдельное задание, после стабилизации формата).
Пауза в любой момент не страшна: файлы лежат у владельца, повторный разбор того же PDF даёт тот же результат (контрагенты уже в справочнике).

## 5. Стандартный XLSX «Операции + Сверка»
Имя файла: `<банк>_<ГГГГ-ММ>.xlsx` (уточняется, раздел 13).

**Лист «Операции»** (порядок строк = порядок в выписке, нужен для цепочки остатков):
| Колонка | Содержание |
|---|---|
| № | номер строки в выписке (сквозной) |
| Дата | первая дата выписки (раздел 3, п. 4) |
| Время | время карточной операции из описания или пусто |
| Счёт | 4 последние цифры признака счёта (счёт/карта по правилам банка); полные номера в файл не кладём |
| Контрагент | опознанный контрагент (из шага контрагентов) |
| Сумма | со знаком: приход плюс, расход минус; число, не текст |
| Валюта | код валюты операции |
| Остаток после | остаток после операции, как в выписке |
| Описание из выписки | полный исходный текст операции (склеенные строки), чтобы глазами проверить контрагента |

**Лист «Сверка»**: по строке на счёт/карту: начальный остаток, вклады, выборы, конечный остаток (из шапки выписки или вычисленные), число строк, результат цепочки (ОК или номер первой строки, где не сошлось). Строки операций с расхождением подсвечиваются красным.
Сверка каждого счёта: `остаток_после[i] = остаток_после[i-1] + сумма[i]` (+ комиссия, если есть колонка), первый остаток = начальный + первая сумма; итоги вкладов и выборов совпадают с шапкой. Расчёт в целых минорных единицах (без float).

## 6. Файл контрагентов (до файла операций)
Создаётся приложением по выписке. Читает справочник из базы, пишет в базу только при загрузке.
- **Лист 1 «Выписка»**: колонка 1 «Контрагент в выписке» (уникальные значения из файла, по одному разу); колонка 2 «Опознанный контрагент» (заполняется приложением, если признак уже есть в справочнике; иначе пусто).
- **Лист 2 «Справочник»**: весь справочник контрагентов (для выбора и копирования имён).
- **Работа владельца**: смотрит неопознанных и опознанных; находит нужного в справочнике и вписывает его имя во вторую колонку; поправляет, если опознано неверно; для реально нового оставляет пусто.
- **Загрузка обратно** (всё или ничего):
  - колонка 2 заполнена и имя есть в справочнике: операции привязываются к этому контрагенту, текст из колонки 1 добавляется ему как ещё один признак (если его ещё нет);
  - колонка 2 заполнена, но такого имени в справочнике нет (опечатка): **файл не принимается**, сообщение с номером строки, ничего не записывается;
  - колонка 2 пустая: создаётся новый контрагент (имя из колонки 1, тип «организация» по умолчанию, как в `DECISIONS.md` от 15.11.2026), текст из колонки 1 становится его признаком.
- Если новых нет и всё опознано, файл всё равно можно выгрузить кнопкой (для проверки).
- Автоматической «чистки» имён (Lidl dakuje 185-BRATISLAVA → Lidl) нет: чистое имя выбирает владелец через колонку 2; дубли вроде «Lidl dakuje 165» и «185» сводятся к одному контрагенту добавлением признаков.
- Для SEPA признак контрагента: IBAN без пробелов (в базе только хэш и `last4`, как для счетов) плюс имя из «Názov protiúčtu». Для карточных: название торговой точки до даты операции.

Настройки делаются один раз на шаблон. Если шаблон не сошёлся со сверкой, файл всё равно выдаётся с пометкой.
Колонка «Счёт» для Словакии: 4 последние цифры IBAN счёта (карта 4324 остаётся в описании; уточняется, раздел 13).

## 8. Технологии
- Разбор PDF: `pdfjs-dist` (локально в браузере/Node, данные никуда не уходят). Подключать динамически (`import()`), чтобы не раздувать основной пакет PWA.
- Чтение и запись XLSX: предлагается **ExcelJS** (MIT): нужны подсветка красным и несколько листов; бесплатная версия SheetJS стили не пишет. Подключать динамически. Решено 20.11.2026 (раздел 13).
- Деньги: целые минорные единицы (`src/core/money.ts`), без float.
- Тесты: только на **выдуманных** данных (репозиторий публичный). Для PDF Словакии тесты работают на массиве «слов с координатами», собранном вручную в фикстуре. Реальный PDF владельца проверяется только на его телефоне.

## 9. Экран и навигация

- Нижнее меню: пункт «Движения» заменяется на «Выписки»; сам экран «Движения» переносится в «Прочее» отдельной строкой. Окончательное расположение решим, когда всё наладится.

## 14. Реализация ядра разбора (пункт 1, 21.11.2026)

**Где:** `src/core/statements/` (`types.ts` модель, `slsp.ts` разбор PDF Словакии, `reconcile.ts` сверка, `pdfText.ts` слова с координатами через `pdfjs-dist`, динамический импорт, `index.ts`). Тесты: `tests/statements/` (фикстура `slspFixture.ts` строит выдуманные слова в раскладке банка). Коды ошибок: `STATEMENT_UNRECOGNIZED` (не выписка этого банка), `STATEMENT_PARSE` (не разобрана строка или сумма).

**Проверено на реальном PDF SPACE 09.2026** (локально, в репозиторий файл не попал): 5 страниц, **58 операций** (в более ранней записи было 59, это ошибка), сверка сошлась до копейки: цепочка остатков, вклады 2 000,00, выборы 2 591,73, остаток 1 837,31 → 1 245,58.

**Раскладка (из реального PDF, единицы pdfjs, A4 595×842).** Колонки по X из строки заголовка: даты x≈34-136, описание x≈143, «Suma transakcie» заголовок x≈384 (число прижато вправо к 429), «Suma poplatku» x≈435, «Zostatok» x≈503 (число прижато вправо к 561). Классификация числа по правому краю: до x=«Suma poplatku» это сумма, до x=«Zostatok» комиссия, дальше остаток. Операция начинается со строки, где в левых колонках две даты; сумма и остаток лежат на той же Y. Начало таблицы на странице: строка ниже второй строки заголовка («valuty zúčtovania ... po transakcii»); конец: «Poznámka» или «info@slsp.sk». Слова левее x=30 (боковой текст `M010_...`) игнорируются. Шапку берём со страницы 1 по левой и правой половинам (граница x=300); на страницах 2+ проверяется только совпадение номера счёта.

**Модель строки** (`StatementRow`): `n`, `accountKey` (4 последние цифры IBAN), `valueDate`, `bookingDate` (в колонку «Дата» идёт `bookingDate`, как решено), `time` (только у карты, из описания), `title`, `counterparty {kind: card|sepa|other, name, iban}`, `cardMask`, `description` (весь текст одной строкой), `amountMinor`, `feeMinor`, `balanceAfterMinor`, `currency`. Контрагент: карта = торговая точка без даты-времени (`Lidl dakuje 185-BRATISLAVA`); SEPA = «Názov protiúčtu» + IBAN без пробелов.

**Сверка** (`reconcileAccount`): `остаток[i] = остаток[i-1] + сумма + комиссия`; после ошибки цепочка пересинхронизируется по остатку строки (одна ошибка даёт один номер, а не хвост); плюс итоги: приходы, расходы (по модулю), конечный остаток. Результат: `ok`, `badRows`, `firstBadRow`, ожидаемое и посчитанное. Расхождение не бросает ошибку: файл создаётся с пометкой (пункт 4).

**Допущения, пока нет образца с комиссиями:** колонка «Suma poplatku» читается со знаком, как сумма (минус = списание); в итоги «Výbery spolu» комиссия входит как расход. Если на бизнес-счёте (пункт 5) окажется иначе, правится `reconcile.ts` и `slsp.ts`. ## 15. Реализация файла контрагентов (пункт 2, 21.11.2026)

**Где:** `src/core/statements/counterparties.ts` (логика), `cpWorkbook.ts` (XLSX, ExcelJS динамически). Тесты: `tests/statements/counterparties.test.ts`.

**API.** `collectCounterpartyGroups(parsed)` даёт уникальных контрагентов по всем счетам выписки: карта и «иное» по нормализованному названию, SEPA по IBAN. `recognizeGroups(ctx, groups)` ищет в справочнике: сначала по IBAN (HMAC), затем по названию. `buildCounterpartyWorkbook(ctx, parsed)` строит XLSX, `readCounterpartyWorkbook(bytes)` читает его после правок, `applyCounterpartyFile(ctx, rows)` проверяет и пишет одним пакетом.

**Файл.** Лист «Выписка»: 1 «Контрагент в выписке», 2 «Опознанный контрагент» (выпадающий список из «Справочника», ручной ввод разрешён), 3 «Имя нового контрагента», 4 «IBAN (служебное, не менять)» (нужен, чтобы загрузка работала без исходного PDF). Лист «Справочник»: имя, тип.

**Правила загрузки.** Колонка 2 заполнена и имя найдено (регистр и лишние пробелы не важны): контрагенту добавляются признаки (название `statement_name`, при наличии IBAN `account_number`: хэш, шифртекст, `last4`). Имя не найдено или не однозначно: отказ, в сообщении номера строк Excel (до пяти и «и ещё N»), ничего не записано. Колонка 2 пуста: новый контрагент (имя из колонки 3, иначе из колонки 1; тип «организация»); одинаковые новые имена сводятся к одному контрагенту (так «Lidl 165» и «Lidl 185» становятся одним). Если новое имя уже есть в справочнике: отказ (впишите его во 2-ю колонку). Признак, который уже действует у другого контрагента, переходит к выбранному: старый закрывается вчерашним днём (если он заведён сегодня, просто переназначается). Повторная загрузка того же файла ничего не меняет. В журнал пишется одна запись `counterparty_file_loaded` с числами, без номеров.

**Опознание не зависит от даты выписки:** используются признаки, действующие сегодня (иначе контрагенты, заведённые сегодня, не опознались бы в старых выписках).

## 20. Решение проблем (версия 0.2.20, 22.11.2026)
Код: `compare.ts` (`compareWithDb(ctx, st, decisions)`), `statementProblems.ts` (`resolveProblem`, `compareTask`), `identifiers.ts` (`addAccountLast4`), экран `StatementProblemsScreen`. Миграция `20261122200000_iteration11_problem_kinds2.sql` (виды `amount_mismatch`, `date_mismatch`).
**Порядок сравнения по счёту:** 1) «оставить базу» (решение) и точные совпадения дата+сумма (набор с количеством, порядок не важен); 2) та же сумма, дата другая в пределах 3 дней → `date_mismatch`; 3) тот же контрагент и знак, сумма другая, дата в пределах 3 дней, не перевод → `amount_mismatch`; 4) остальные строки новые (перевод без возможности создать пару → `transfer_unpaired`, если не выбрано «обычный»); 5) оставшиеся операции базы внутри периода → `db_only`. Операции базы за допуск вокруг периода участвуют только в поиске пары.
**Решения (`state.decisions`):** `keepDb` (id), `keepBase` и `distinct` ({счёт, строка, id операции}), `plain` ({счёт, строка}). Удаление и «принять сумму» меняют данные сразу (проверка закрытых периодов, журнал); удаление перевода гасит обе записи.
**Признак счёта без шифрования:** хэш SHA-256 от «last4:account_number:цифры:id счёта», в шифр-поле те же 4 цифры (base64). Полного номера нет, просмотр номера не работает.
**Возможные проблемы, решения пока нет (решать по факту обнаружения):** дата расходится (`date_mismatch`, обнаруживается), валюта выписки ≠ валюте счёта (сейчас выглядит как «счёт не найден»), перевод в разных валютах (сейчас `transfer_unpaired`, пары нет), несходящаяся цепочка остатков после записи (пункт 4б-2).

## 21. Шаг 4: сверка остатков и запись (версия 0.2.22, 23.11.2026)

Новый счёт без начального остатка в базе всегда даст «не сходятся»: сначала ввод остатка на дату до периода.

## 23. Начальный остаток из выписки (версия 0.2.24, 23.11.2026)
Модуль `src/core/statements/openingFix.ts`: `planOpeningFixes` (что предложить), `applyOpeningFixes` (применить одним пакетом, только владелец). Время начального остатка: начало локального дня `periodStart` минус 1 мс (пояс счёта).
- **create:** до начала периода записей нет и начального остатка нет. Создаётся корректировка на сумму начального остатка выписки, `isOpening`.
- **move:** до начала периода записей нет, начальный остаток есть, он позже. Считается «объяснено» = остаток выписки + записи базы между началом периода и старым остатком + новые операции выписки. Разница = старый остаток минус «объяснено». Ноль: старый остаток помечается удалённым. Не ноль: он становится обычной корректировкой на разницу, дата = максимум из старой и конца периода выписки плюс 1 мс.
- **нет предложения:** до начала периода есть записи (пропуск или дубль); или новые операции выписки не раньше старого остатка (пересечение, показывается причина).
- Закрытые периоды: ошибка `PERIOD_LOCKED`. Журнал: `opening_created`, `opening_removed`, `opening_to_adjustment`.
