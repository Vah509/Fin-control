# Порядок работы и правила актуальности

## 1. Участники и ограничения

Владелец работает с телефона: нет git и компьютера. Ответы Claude короткие, по-русски. SQL из чата давать **одной строкой, без блоков кода и без `count(*)`** (звёздочки пропадают при копировании; использовать `count(1)`). Большие миграции отдавать файлом.

## 2. Как изменения попадают в репозиторий

1. Claude клонирует репозиторий (сеть к github.com открыта), правит, запускает `npm ci && npm run build && npx vitest run`.
2. Claude отдаёт **ZIP с файлами по их путям в репозитории**. Владелец кладёт ZIP в `ai-updates/`.
3. Автоматизация (`.github/workflows/unzip-and-update.yml`, `scripts/process_update.py`): распаковывает в staging, собирает проект, при успехе копирует файлы в репозиторий, шлёт сообщения в Telegram, всегда удаляет ZIP.
4. Удаление файлов: текст со списком путей (по одному на строке) кладётся в `cleanup-requests/`, затем вручную запускается workflow «Repo Cleanup».
5. SQL-миграции автоматика не применяет: владелец выполняет их в Supabase SQL Editor (сначала тестовый проект). Файл миграции лежит и в репозитории (в ZIP), и в чате.

Что автоматика **не принимает** из ZIP: `.git/`, `.github/`, `scripts/`, `ai-updates/`, `cleanup-requests/`, `node_modules/`, любые `.env` кроме `.env.example`. Изменения в этих местах владелец вносит вручную через веб-интерфейс GitHub; Claude отдаёт такие файлы отдельно от ZIP с инструкцией, куда их положить.

## 3. Правила актуальности документов (обязательны)

Цель: в репозитории всегда лежит всё, чтобы начать работу в любом новом чате без пересказа.

**Каждый ZIP, меняющий код, схему или планы, содержит:**
1. `docs/STATUS.md`: обновлены дата, разделы 4 (что готово), 5 (что ждёт владельца), 6 (ближайшие шаги), 7-8 (вопросы и долги).
2. `docs/CHANGELOG.md`: новая запись сверху (дата, что сделано, какие файлы и миграции затронуты, что проверено, что не проверено).
3. Профильные документы, если затронуты: `docs/ARCHITECTURE.md` (модули, экраны, тесты), `docs/DATA-MODEL.md` (таблицы, миграции), `docs/DECISIONS.md` (новые решения и их дата), `docs/ROADMAP.md` (закрытые и новые пункты).
4. Новые миграции только как новые файлы `supabase/migrations/ГГГГММДДччммсс_название.sql`. Применённую миграцию не править: нужна новая.

**Перед отправкой ZIP Claude проверяет:**
- числа в документах (количество тестов, список экранов, список миграций) совпадают с фактом;
- каждое решение владельца из чата записано в `docs/DECISIONS.md` с датой;
- каждый открытый вопрос либо в `docs/DECISIONS.md` (раздел 3), либо снят;
- в ответе владельцу перечислено, что менялось в документах.

**Ответ Claude владельцу в конце работы** содержит: что сделано, что проверено и чем, что не проверено, что делать владельцу (по пунктам), какие вопросы нужны.

Если ZIP не содержит `docs/STATUS.md` и `docs/CHANGELOG.md`, автоматика присылает предупреждение в Telegram (проверка в `scripts/lib/checks.py`, см. раздел 6).

## 4. Определение «готово»

Шаг готов, когда: код собран (`npm run build`), тесты зелёные, новые правила покрыты тестами ядра на памяти, документы обновлены по разделу 3, миграции (если есть) проверены в песочнице и отданы владельцу с инструкцией. «Проверено владельцем на телефоне» отмечается в `docs/STATUS.md` только по его подтверждению.

## 5. Как начать новый чат

Первая фраза: «Прочитай docs/STATUS.md в репозитории Vah509/Fin-control (клонируй) и продолжи с пункта N из раздела 6». В файлах проекта Claude лежит `START-HERE.md` с тем же. Бриф v2 и дополнение v3 в файлах проекта описывают замысел, но имеют приоритет ниже, чем `docs/`.

## 6. Автоматизация: что где лежит

- `.github/workflows/unzip-and-update.yml`: запуск при появлении `ai-updates/*.zip`, Node 22, Python 3.12.
- `.github/workflows/repo-cleanup.yml`: ручной запуск удаления по списку.
- `scripts/process_update.py`, `scripts/process_cleanup.py`, `scripts/lib/` (`safe_zip.py`, `staging.py`, `test_build.py`, `checks.py`, `send_telegram.py`).
- Секреты репозитория: `TELEGRAM_TOKEN`, `TELEGRAM_TO`.
- Проверки `checks.py` мягкие: предупреждения в Telegram, обновление не блокируют.

## 7. Будильник базы (Cloudflare Worker)

Бесплатная база Supabase засыпает после недели без запросов. Worker `keep-alive` раз в сутки (Cron `0 6 * * *`) вызывает функцию `public.keep_alive()` (возвращает 1, право `execute` для `anon`). Пошаговая инструкция с кодом Worker, переменными и проверкой: **`docs/keep-alive-worker.md`**. Функция лежит в миграции `supabase/migrations/20261113100000_keep_alive.sql` (идемпотентная: безопасна, если уже создана вручную). Статус настройки владельцем: не подтверждён. После переезда данных на SQLite Worker не нужен.
