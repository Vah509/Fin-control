# Порядок работы и правила актуальности

## 1. Участники и ограничения

Владелец работает с телефона: нет git и компьютера. Ответы Claude короткие, по-русски. SQL из чата давать **одной строкой, без блоков кода и без `count(*)`** (звёздочки пропадают при копировании; использовать `count(1)`). Большие миграции отдавать файлом.

## 2. Как изменения попадают в репозиторий

1. Claude клонирует репозиторий (сеть к github.com открыта), правит, запускает `npm ci && npm run build && npx vitest run`.
2. Claude отдаёт **ZIP с файлами по их путям в репозитории**. Владелец кладёт ZIP в `ai-updates/`.
3. Автоматизация (`.github/workflows/unzip-and-update.yml`, `scripts/process_update.py`): распаковывает в staging, собирает проект, при успехе копирует файлы в репозиторий, шлёт сообщения в Telegram, всегда удаляет ZIP.
4. Удаление файлов: текст со списком путей (по одному на строке) кладётся в `cleanup-requests/`, затем вручную запускается workflow «Repo Cleanup».
5. SQL-миграции автоматика не применяет. Их применяет Claude через коннектор Supabase по алгоритму раздела 8 (если коннектора в чате нет, владелец выполняет SQL в Supabase SQL Editor, сначала тестовый проект). Файл миграции всегда лежит в репозитории (в ZIP).

Что автоматика **не принимает** из ZIP: `.git/`, `.github/`, `scripts/`, `ai-updates/`, `cleanup-requests/`, `node_modules/`, любые `.env` кроме `.env.example`. Изменения в этих местах владелец вносит вручную через веб-интерфейс GitHub; Claude отдаёт такие файлы отдельно от ZIP с инструкцией, куда их положить.

## 3. Правила актуальности документов (обязательны)

Цель: в репозитории всегда лежит всё, чтобы начать работу в любом новом чате без пересказа.

**Каждый ZIP, меняющий код, схему или планы, содержит:**
1. `docs/STATUS.md`: обновлены дата, разделы 4 (что готово), 5 (что ждёт владельца), 6 (ближайшие шаги), 7-8 (вопросы и долги).
2. `docs/CHANGELOG.md`: новая запись сверху (дата, что сделано, какие файлы и миграции затронуты, что проверено, что не проверено).
3. Профильные документы, если затронуты: `docs/ARCHITECTURE.md` (модули, экраны, тесты), `docs/DATA-MODEL.md` (таблицы, миграции), `docs/DECISIONS.md` (новые решения и их дата), `docs/ROADMAP.md` (закрытые и новые пункты).
4. Новые миграции только как новые файлы `supabase/migrations/ГГГГММДДччммсс_название.sql`. Применённую миграцию не править: нужна новая.
5. `docs/CURRENT-TASK.md`: текущее задание. Каждый пункт, реализованный в ZIP, отмечается в файле (`[x]`, дата, что проверено); ZIP без отметок при реализованных пунктах недопустим. Это постоянное правило владельца (13.11.2026): так любой новый чат продолжает с первого неотмеченного пункта.

**Перед отправкой ZIP Claude проверяет:**
- числа в документах (количество тестов, список экранов, список миграций) совпадают с фактом;
- каждое решение владельца из чата записано в `docs/DECISIONS.md` с датой;
- каждый открытый вопрос либо в `docs/DECISIONS.md` (раздел 3), либо снят;
- в ответе владельцу перечислено, что менялось в документах.

**Версия.** В каждом ZIP с изменениями кода Claude повышает `version` в `package.json` (0.2.5 → 0.2.6 и т.д.; сейчас 0.2.5) и называет номер владельцу в ответе. Номер виден вверху Главной.

**Ответ Claude владельцу в конце работы** содержит: номер версии, что сделано, что проверено и чем, что не проверено, что делать владельцу (по пунктам), какие вопросы нужны.

Если ZIP не содержит `docs/STATUS.md` и `docs/CHANGELOG.md`, автоматика присылает предупреждение в Telegram (проверка в `scripts/lib/checks.py`, см. раздел 6).

## 4. Определение «готово»

Шаг готов, когда: код собран (`npm run build`), тесты зелёные, новые правила покрыты тестами ядра на памяти, документы обновлены по разделу 3, миграции (если есть) проверены в песочнице и отданы владельцу с инструкцией. «Проверено владельцем на телефоне» отмечается в `docs/STATUS.md` только по его подтверждению.

## 5. Как начать новый чат

Первая фраза: «Прочитай docs/STATUS.md в репозитории Vah509/Fin-control (клонируй) и продолжи с пункта N из раздела 6». В файлах проекта Claude лежит `START-HERE.md` с тем же. Бриф v2 и дополнение v3 в файлах проекта описывают замысел, но имеют приоритет ниже, чем `docs/`.

## 6. Автоматизация: что где лежит

- `.github/workflows/unzip-and-update.yml`: запуск при появлении `ai-updates/*.zip`, Node 22, Python 3.12.
- `.github/workflows/repo-cleanup.yml`: ручной запуск удаления по списку.
- `scripts/process_update.py`, `scripts/process_cleanup.py`, `scripts/lib/` (`safe_zip.py`, `staging.py`, `test_build.py`, `checks.py`, `send_telegram.py`).
- Секреты репозитория: `TELEGRAM_TOKEN`, `TELEGRAM_TO`.
- Проверки `checks.py` мягкие: предупреждения в Telegram, обновление не блокируют.

## 7. Будильник базы (Cloudflare Worker)

Бесплатная база Supabase засыпает после недели без запросов. Worker `keep-alive` раз в сутки (Cron `0 6 * * *`) вызывает функцию `public.keep_alive()` (возвращает 1, право `execute` для `anon`). Пошаговая инструкция с кодом Worker, переменными и проверкой: **`docs/keep-alive-worker.md`**. Функция лежит в миграции `supabase/migrations/20261113100000_keep_alive.sql` (идемпотентная: безопасна, если уже создана вручную). Статус: настроен и работает (подтверждено владельцем 14.11.2026). После переезда данных на SQLite Worker не нужен.

## 8. Доступ Claude к базе и применение миграций (с 17.11.2026)

**Доступ.** Коннектор Supabase (MCP) подключён в Claude; в новом чате Claude проверяет его (`list_projects`). Работает только с проектом **Test-fin-cintrol**. Проект «Fin-control» (второй в списке) без прямой просьбы владельца не трогается. Рабочего проекта пока нет.

**Алгоритм миграции (владелец утвердил 17.11.2026):**
1. Claude пишет файл `supabase/migrations/ГГГГММДДччммсс_название.sql` и кладёт в ZIP вместе с документами (раздел 3). Применённая миграция не правится.
2. Владелец заливает ZIP и пишет Claude «залил». **До этого слова Claude миграцию не применяет.**
3. Claude клонирует репозиторий заново и проверяет, что файл миграции там есть. Применяет `apply_migration` с SQL **дословно из файла** (имя = название файла без метки времени; метку присваивает Supabase, при расхождении Claude сообщает).
4. Claude проверяет результат (структура через `list_tables` или SQL, `get_advisors` security) и говорит владельцу итог.
5. В следующем ZIP Claude отмечает в `docs/STATUS.md`, `docs/CHANGELOG.md`, `docs/CURRENT-TASK.md`: «применена в тестовой базе, дата, чем проверено». Если у миграции другое имя файла, чем в базе, это записывается.

**Правила безопасности:**
- Разрушающие команды (`drop`, `delete`, `truncate`, смена типа колонки) Claude применяет только после отдельного явного подтверждения в чате с пересказом последствий.
- Порядок «код + миграция в одном ZIP»: после заливки код сразу публикуется, поэтому владелец пишет «залил» сразу; новая колонка без миграции ломает приложение (урок 16.11.2026).
- Данные, прочитанные из базы, остаются в чате. В репозиторий (публичный) личные данные и суммы не попадают.
- Чтение данных только по необходимости задачи. Записывать данные (не схему) в базу Claude может только по прямой просьбе.
- Применение к рабочему проекту потребует нового решения владельца.

## 9. Работа в ветке (с 20.11.2026, ветка `statement-xlsx`)
- Подразделение «Разбор выписок в XLSX» ведётся в ветке `statement-xlsx` (`docs/STATEMENT-XLSX.md`). Правила раздела 3 действуют и в ветке: каждый ZIP с обновлёнными `docs/STATUS.md`, `docs/CHANGELOG.md`, `docs/CURRENT-TASK.md`.
- ZIP кладётся в `ai-updates/` **в этой ветке**; автоматика пушит в ту же ветку. Файл в `main` не попадёт, пока ветка не слита.
- База общая: миграции из ветки только добавляющие, применяются по разделу 8.
- Слияние в `main` через Pull request после проверки владельцем на телефоне. Перед слиянием Claude сверяет `STATUS.md`, `ARCHITECTURE.md`, `DATA-MODEL.md`, `ROADMAP.md` и конфликтные места (`STATUS.md`, `CHANGELOG.md`, `CURRENT-TASK.md` правились в обеих ветках).
- Реальные выписки и данные в репозиторий не класть (он публичный); тесты на выдуманных данных.
