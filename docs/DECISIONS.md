## 2026-11-21: решения по файлу операций и сверке с базой (владелец, версия 0.2.17)
1. **Времени в файле нет.** Колонка «Время» убрана (решение владельца). Причина: у SEPA времени нет, у карточных оно из описания и может относиться к другому дню; нужна только дата и остаток. Порядок строк в дне задаёт «№» (порядок выписки). Остаток на конец дня = «Остаток после» последней строки дня.
2. **Комиссия отдельной строкой-расходом** сразу после своей операции (колонка «Комиссия» убрана): контрагент «Комиссия банка», тот же «№», остаток после операции без комиссии, потом после комиссии.
3. **Сравнение выписки с базой перед записью.** Ключ: счёт + дата списания + сумма + валюта; одинаковые строки как набор с количеством, порядок не важен. Норма: есть в выписке (нет в базе: будет записано; есть в базе: ничего). Проблема: есть в базе, нет в выписке (`db_only`), требует ручного решения. Корректировки (стартовые остатки, учёт остатками), удалённые и чужой период в сравнение не входят. Расхождение в сумме тоже проблема (решается позже).
4. **Файл только для просмотра**, обратно не загружается; колонки «В выписке» и «В базе» (плюсы); строки «только в базе» в конце жёлтым. Колонка «Соответствует №» и обратная загрузка файла (пункт 9 в прежнем виде) отменены.
5. **Таблица проблем** `statement_problems` привязана к задаче; удаление задачи без «Готово» стирает её проблемы. Кнопка «Проблемы» открывает экран списка (пока только просмотр, решений нет). Если проблем нет, активна «Готово»; **пока «Готово» только закрывает задачу и в базу ничего не пишет**, запись включим в 0.2.19 по слову владельца.
6. **Переводы между своими счетами (план 0.2.19, не сделано):** одна валюта на обоих счетах: сразу две записи (расход и приход) с общим `transfer_id`. Разные валюты: запись на стороне загружаемой выписки, а для второго счёта запоминается «ожидаемая пара» (дата, сумма, валюта, откуда); когда придёт выписка второго счёта, строка находит её и они связываются. Допуск по дате при поиске пары и разбор проблем решаем, когда дойдём до работы с проблемами. Закрытие периодов и срезы пока не трогаем (отдельная большая тема).
7. Счёт выписки ищется в базе по последним 4 цифрам признака `account_number` (без ключей шифрования в приложении) и совпадению валюты; не нашёлся или неоднозначен: сравнения по нему нет, на странице задачи предупреждение.

## 2026-11-22: запись операций выписки по «Готово» включена (версия 0.2.19)
1. «Готово» записывает в `transactions` новые операции выписки одним пакетом (`apply_batch`) и закрывает задачу. Условия: сравнение было, **сверка выписки сошлась** (иначе `RECONCILE_FAILED`), **проблем нет** (сравнение повторяется при нажатии; если проблемы появились, они сохраняются и запись не идёт). Строки, уже найденные в базе, не пишутся: повторная загрузка ничего не задваивает.
2. Время в базе: 12:00 по поясу счёта + номер строки в секундах (порядок внутри дня); не показывается. `source = 'import'`, `raw = {n, description}`, `dedupe_hash` пока не считается (дубли ловит сравнение по дате и сумме).
3. Типы: знак суммы (income/expense); комиссия отдельной записью `fee` (если комиссия положительная, `income`); перевод на свой счёт `transfer`.
4. Перевод на свой счёт (контрагент `own_account` с `account_id`): если счёт-получатель есть в базе, не архивный и в той же валюте, пишутся две записи (эта сторона и парная с обратным знаком) с общим `transfer_id`. Иначе проблема `transfer_unpaired` (другая валюта, контрагент не привязан к счёту, архивный счёт), запись блокируется. Ожидаемая пара для разных валют (отдельная таблица) пока не сделана.
5. Счёт выписки не найден в базе (нет признака `account_number` с последними 4 цифрами и валютой): проблема `account_missing`, запись блокируется.
6. Закрытые периоды: проверка `assertUnlocked` по самой ранней дате на каждом счёте (в том числе счёте-получателе); при закрытом периоде запись отклоняется целиком (`PERIOD_LOCKED`).
7. Известное ограничение: если банки проводят одну и ту же операцию в разные даты, сравнение по дате не свяжет их (будут проблема `db_only` и новая строка). Допуск по дате и экран решения проблем делаются позже. Сверка цепочки остатков в базе после записи пока не делается.

## 2026-11-23: начальный остаток из выписки (версия 0.2.24)
Решение владельца. Шаг 5: если начало не сходится и до начала периода в базе нет записей, предлагается создать начальный остаток выписки на начало периода. Выписки могут грузиться не по порядку: если начальный остаток уже есть позже, он передвигается на начало этой выписки. Прежний остаток удаляется, когда движения его объясняют (конец выписки равен ему), иначе становится корректировкой на разницу («неучтённая», принцип 2 брифа); её дата не раньше конца периода выписки, чтобы не ломать проверку этой выписки. Если записи до начала периода есть, остаток не предлагается (ошибка, не отсутствие старта). Подробности: `STATEMENT-XLSX.md`, раздел 23.
Открыто: граница между соседними выписками при пропуске: разница лежит на стыке, поэтому проверка начала следующей выписки покажет её. Целиком решит отдельная функция целостности счёта (`CURRENT-TASK.md`, 4б-5).
