# Fin-control: состояние проекта и план (обновлено 12 ноября 2026)

Главный файл для любого нового чата. Читать целиком, потом `docs/` и код. Где он расходится с брифом v2, дополнением v3 и `db-schema-iteration-1.md` (лежат в файлах проекта Claude), **верен этот файл**. Актуальная схема базы: `supabase/migrations/` (файл `db-schema-iteration-1.md` устарел).

## 1. Что это

Личное приложение учёта денег в разных местах, странах и валютах. Главный сценарий: срез остатков на выбранную дату. Второй: движения (откуда пришло, куда ушло).
Владелец: Вахтанг (живёт в Братиславе), общается по-русски, работает **с телефона** (git и компьютера нет). Ответы коротко, по-русски.

## 2. Репозиторий и как развернуть

- Адрес: https://github.com/Vah509/Fin-control (`git clone https://github.com/Vah509/Fin-control.git`). Claude в песочнице чата клонирует его сам (сеть к github.com открыта).
- Стек: Vite + React + TypeScript, Supabase (Postgres, Auth, RLS), хостинг Cloudflare Pages (сборка из репозитория автоматически).
- Проверка локально: `npm ci`, `npm run build` (включает `tsc`), `npx vitest run` (91 тест). `npm run test:supabase` против реального тестового проекта нужны переменные `TEST_SUPABASE_URL`, `TEST_SUPABASE_ANON_KEY`, `TEST_USER_EMAIL`, `TEST_USER_PASSWORD` (в терминале, не в git); пока не запускался.
- Переменные Cloudflare Pages: `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` (publishable-ключ, публичный). Сервисный ключ нигде не используется.
- Тестовый проект Supabase: Test-fin-cintrol (Ireland). Рабочего проекта пока нет. В тестовую базу ранее загружен seed (20 счетов, 45 контрагентов, группы тегов, 2 стартовые корректировки).

### Как Claude доставляет изменения
Claude готовит **ZIP с изменёнными файлами по их путям в репозитории** и отдаёт владельцу. Владелец кладёт ZIP в папку `ai-updates/` репозитория, автоматизация (GitHub Actions) распаковывает, собирает, при успехе копирует файлы и шлёт сообщение в Telegram. Удаление файлов: текстовый список в `cleanup-requests/`. Автоматизация **не принимает `.github/`** и `.env`. SQL-миграции владелец применяет вручную в Supabase SQL Editor (файл миграции лежит и в репозитории, и отдельно в чате).
Договорённость: SQL, который владелец копирует из чата, давать **одной строкой без блоков кода и без `count(*)`** (использовать `count(1)`, звёздочки пропадают при копировании). Большие миграции отдавать файлом.

## 3. Архитектура (принцип: вся логика в TypeScript, база только хранилище)

```
src/core/      все правила: срез, курсы, округление, закрытие периодов, проверки, остатки,
               счета и разделы, порядок, ключи, оформление, выгрузка/загрузка (dump), журнал
src/data/      types.ts, storage.ts (интерфейс), supabase/ (сейчас), memory/ (тесты), sqlite/ (позже)
src/auth/      вход (email+пароль), роль владельца
src/ui/        экраны (вызывают только ядро), app.tsx (контекст), parts.tsx, format.ts
tests/         тесты ядра на памяти, контрактные тесты хранилищ, ui-format
supabase/migrations/   схема и права
public/        manifest.webmanifest, иконки
```
Суммы: целые минорные единицы, без float. Время ISO UTC, «конец дня» в поясе счёта. Запись только онлайн. Запись пакета атомарно: `rpc('apply_batch')`.
Конечная цель: Android (Capacitor) с локальной SQLite, тот же код; Supabase станет необязательным облаком. Телефон первоисточник.

## 5. Что нужно сделать владельцу сразу

1. Применить `supabase/migrations/20261111100000_iteration4_editing_global_lock.sql` в SQL Editor (сначала тестовый проект). Без неё не заработают создание счетов и разделов, закрытие периодов, журнал. Миграция идемпотентна.
2. Залить ZIP 4в в `ai-updates/`, проверить на телефоне: создать тестовый счёт, переименовать, поменять иконку, переставить, перенести в другой раздел, создать раздел, закрыть и открыть период.
3. Cloudflare Worker «будильник» (раздел 7).
4. По желанию `npm run test:supabase`.

## 6. Принятые решения (по порядку появления)

- Шифрование полных номеров счетов откладывается до импорта выписок; сейчас в базе только `last4`, экраны без признаков счетов.
- Загрузка файла выгрузки в Supabase это слияние по id (не полная замена); запрещено при действующем закрытии.
- Выгрузка пока открытым JSON; шифрование паролем позже.
- **Закрытие периода общее для всех счетов** (решение владельца 11 ноября): за период всё сведено и остатки точные. Разделы (в БД `projects`) только группы для показа и фильтра. Перенос счетов между разделами свободный. В `period_locks` у новых записей `project_id` пустой; текущее закрытие = последняя действующая запись.
- Курсы валют запрашивает **приложение** (кнопка «Обновить курсы», возможно при открытии), не Worker: после переезда на Android данные будут в локальной SQLite. Предложение: monobank `/bank/currency` (публичный, без токена, не чаще раза в 5 минут), среднее между покупкой и продажей, источник `mono`; Приват не проверялся; для истории возможен НБУ по датам. Нужно проверить CORS для PWA (при проблеме прокси). Не реализовано.
- Оформление счёта: сначала цветная иконка (8 цветов, 12 иконок в `src/core/appearance.ts`), потом карточки в стиле банковских.
- База Supabase бесплатного плана засыпает за неделю без запросов: Worker раз в сутки делает `keep_alive` (раздел 7). Когда данные уйдут в SQLite, Worker не нужен.

## 7. Будильник базы (Cloudflare Worker)

Одна SQL-функция `public.keep_alive()` (возвращает 1, право `execute` для `anon`) и Worker `keep-alive` с Cron `0 6 * * *`, переменные `SUPABASE_URL`, `SUPABASE_ANON_KEY`. Подробная инструкция была отдана файлом `keep-alive-worker.md`. Статус настройки владельцем: не подтверждён.

## 8. Известные ограничения и долги

- В репозитории **нет миграции итерации 2** (контрагенты, группы тегов, теги, внешние ключи операций): в тестовой базе она применена вручную. Её SQL надо восстановить и положить в `supabase/migrations/` до создания рабочего проекта.
- Миграция 4в удаляет функции `close_period`, `reopen_period`, `locked_through(uuid)` (логика закрытия теперь в ядре) и переписывает `apply_batch` (вставка новых строк, затем обновление, удаление операций раньше записи, составной ключ `account_access`). Триггеры `b_period_lock` в БД остаются как защитный слой и теперь смотрят на общее закрытие.
- Карточка счёта правит название, раздел, цвет, иконку, архив. Не правятся пока тип, валюта, страна, учреждение, держатель, режим учёта. У разделов есть поля порядка и оформления, UI оформления разделов нет. Нет создания учреждений.
- Строгое закрытие при расхождениях контрольных точек (`CHECKPOINT_MISMATCH`, обход флагом) и принцип «записать пакет» реализованы, но владелец явно не утверждал.
- Вкладка «Движения» без ввода. «Нет курса» в срезах, пока нет курсов.
- Если у существующих счетов нет строки в `account_access` для владельца, они не видны; новые счета получают доступ при создании.
- Проверено на локальном Postgres с RLS (11 сценариев записи) и в jsdom; на реальном Supabase и на телефоне 4в не запускалось.
